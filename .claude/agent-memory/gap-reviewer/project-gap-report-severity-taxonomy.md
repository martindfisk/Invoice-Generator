Severity in `docs/gaps/gap-report.json` is rule-derived, not hand-set: R1 blocking = standard-mandated term the mandated syntax renders no element for; R2 should-fix = syntax renders it but operation can't carry it, OR a required spec pointer with no model field; R3 note = optional/not applicable; R4 platform = note, only when the capture proves fiskaly fills it (definitions in `docs/gaps/README.md`; implementation `frontend/src/gap-report.ts` severityFor ~line 162 — order: R3 not-applicable, R4 platform, R1, R2, R3 fallback).

R4 is mechanically FatturaPA-only: `platform` comes from `fateFor(format, pointer)` and `FATES_BY_FORMAT` (uapi-field-fate.ts ~line 367) contains only `fatturapa` — the sole capture is docs/reference/fatturapa/ (2026-08-25). So no cii/ubl/xrechnung row can ever be R4-note, and rows without a JSON pointer (pure lossy fields) get `fate: undefined` even for fatturapa — which is why all 24 seller.address|json rows across all four formats are R2 should-fix despite the FatturaPA capture proving Sede is platform. The one R4 row in the report: `fatturapa|payment.meansCode|xml`. Confirmed 2026-09-07 for the five cii seller.address json rows (city/country/number/postCode/region): should-fix correct — not R1 (missingFrom=json + cii-map partyRows lines 84-119 render all five; README lines 56-57 explicitly de-block seller-from-Taxpayer), not note (no CII capture licenses R4; R2 branch precedes R3 fallback regardless of 0..1 cardinality).

**Why:** severity-correct verdicts hinge on these definitions, not on EN 16931 cardinality alone — a `missingFrom: model` row can never be R1-blocking because R1 is about syntax rendering, not model coverage.

**How to apply:** for R2 rows citing "required spec pointer", verify conditionality by walking the active spec (`spec/spec.json` names it): a pointer is _conditionally_ required when it sits in a `required:` array of a schema whose ancestor is optional (e.g. `TaxRepresentative.required=[name,vat_number,country]` but `tax_representative` absent from `InvoiceTransaction.required`; `PersonName.required=[gender,forename,surname]` under optional `name` under optional `details`). Truly optional siblings (prefix/infix/suffix, fiscal_location region) got R3-note — the mechanical split is exactly required-array membership.
