# Demo storyline (≈ 15 minutes, send-only — there is no Receive step)

Personas: **Seller** (org A, Unit key) and **Buyer** (org B, Unit key) in fiskaly TEST; the flow always sends as the seller — the buyer persona exists for the Test runner. **Eleven presets**: reference scenarios (IT SDI, BE Peppol), a German hotel group (XRechnung / ZUGFeRD-CII, Peppol or EMAIL channel) and Roman restaurant scenarios (FatturaPA, including a **TD04 credit note** that composes a `TRANSACTION::CORRECTION`); deliberately broken presets are labelled (wrong VAT sum, missing buyer country, exemption without reason, `0000000` without PEC).

| Act              | User does                                         | Left pane shows                                                                                                                            | Right pane shows                                      | Talking point                                                                            |
| ---------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 0 Setup          | opens app, checks MOCK/LIVE badge, picks a preset | preset cards, format/country meta — no UAPI calls                                                                                          | — (entity reads live in the Test runner's EntityTree) | one API for IT, BE and DE; MOCK replays fixtures through the live code path              |
| 1 Mapper         | edits in any of the **three panes**               | Human view with BT/FPA badges · **fiskaly JSON operation** (what Send posts) · predicted XML; spec-coverage line offers unpopulated fields | —                                                     | the JSON operation is the artifact you author; one model, three national syntaxes        |
| 2 Validate       | runs validation, breaks the XML by hand, re-runs  | stage stepper, findings highlight XML + field                                                                                              | `POST /api/validate/xsd`                              | local checks ≠ acceptance by SDI/Peppol; layered rules (contract → XSD → Schematron/SDI) |
| 3 Send           | clicks Send                                       | INTENTION → TRANSACTION::INVOICE → transmission polling → COMPLETED; DiffView local vs compliance artifact                                 | 2× `POST /records`, polls, `?compliance-artifact`     | fiskaly generates and transmits; the diff shows what fiskaly added/normalised            |
| 4 Second country | repeats 1–3 with the BE or DE preset in 2 minutes | same                                                                                                                                       | same                                                  | same integration, different network and format                                           |

Error demos (pick two): recipient without `invoicing` → COMPLETED with ERROR log, nothing sent · `0000000` without PEC → 4xx · IT recipient without `region` → async FAILED · wrong `X-Api-Version` → 400 · replayed idempotency key → `X-Idempotency-Replayed: true`.

Legal context per country: Italy — D.Lgs. 127/2015, SDI, FatturaPA specs 1.9.1, B2B + B2C, 10-year archive; Belgium — B2B Peppol BIS 3.0 mandatory 1 Jan 2026 (law of 6 Feb 2024), BOSA; EU — Directive 2014/55/EU, EN 16931, ViDA digital reporting on the horizon. Close: "one integration, structured data in, compliant XML out, both directions, with full visibility of every API call."
